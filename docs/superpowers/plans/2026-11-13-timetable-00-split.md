## Rules that keep the two tracks from colliding

1. **Migration numbers are reserved.** 0021 = plan 1 (used). 0022 = plan 2 (used). 0023 = plan 5a.
   0024 = plan 6. 0025 = plan 7. Never renumber; a plan that needs a second migration takes the
   next free number after 0025 and says so in the PR.
2. **Schema.** Track A owns `lib/db/schema-timetable.ts`. Plan 6 (track B) adds `tt_constraints`
   at the end of that file; plan 7 adds the run and solution tables after it. Append only.
3. **The solver contract lives in plan 5a** (`lib/timetable/solver-contract.ts`, Task 4). Maor
   reviews that PR. After it merges, a change to the contract is its own small PR that both read.
4. **Constraint types.** The parameter shape of each type is fixed in the table under plan 6.
   Maor builds the form and Zod schema for a type (`lib/timetable/constraints/<type>.ts`); Ofek
   builds its encoder (`solver/constraints/<type>.py`). The solver never sees labels or names:
   the export turns a label into teacher ids.
5. **Files.** Track A: `lib/timetable/` (except `constraints/`), `solver/`, `scripts/seed-timetable-demo.ts`,
   `app/api/v1/timetable/boards/[board]/runs/**`, generate and edit screens. Track B: `lib/profile/`,
   `components/profile/`, `lib/timetable/constraints/`, `components/timetable/setup/`,
   `components/timetable/constraints/`, the other routes under `app/api/v1/timetable/`.
6. **Messages.** Plan 5b owns `timetable.boards.*` and `timetable.setup.*`; plan 6
   `timetable.constraints.*` and `timetable.collect.*`; plan 7 `timetable.generate.*`; plan 8
   `timetable.edit.*` and `timetable.me.*`. Add keys at the end of the namespace.
7. **Demo data.** The seed writes only into a board named `הדגמה` of the school it is pointed
   at, and only on a local or staging database. Staging is a copy of production
   (`scripts/refresh-staging-db.sh`): a refresh removes the demo board, the `timetable` service
   flag and any labels entered on staging. Re-enable the service on `/platform/schools` and
   re-run the seed after a refresh.
8. Project rules apply everywhere: no direct commits to `main`, merge commits only after all
   checks are green, `pnpm build` passes, no worktrees, production data is never read.

## Outlines

### Plan 4: solver service (track A)
- First task, timeboxed to one day: **benchmark and host.** A synthetic 250-teacher input
  (6 grades x 8 classes, generated by the plan 5a generator with placeholder teachers only) and
  the seeded Kfar Galim input, solved locally with 60 and 300 second limits. Then read Vercel's
  current documentation for Python functions on our plan (duration, memory, bundle size) and
  try the solver as a Python function. It stays there if the Kfar Galim-size solve fits with
  2x headroom; otherwise the same code goes into a small container, and the cost is written
  down. Result: a short section added to the spec, not a separate document.
- `solver/`: CP-SAT model, one encoder per constraint type in `solver/constraints/<type>.py`,
  pytest with one test per type, `solver/fixtures/tiny.json` (from plan 5a) as a golden test.
- Always enforced: a teacher or a class is never in two places at once; a block with
  `consecutive` gets adjacent periods on one day.
- User "hard" constraints carry a very large penalty so a result always returns.
- `mode: evaluate`: fixed placements in, violations out.
- Done when: the fixture solves; each constraint type has a passing test; `evaluate` reports
  the same violations the solver would; the seeded Kfar Galim board solves on the chosen host.

### Plan 7: generate, compare, view (track A)
- Migration 0025: `tt_runs`, `tt_solutions`, `tt_placements`, `tt_boards.published_solution_id`.
- `lib/timetable/solver-client.ts`, run lifecycle, polling. Three weight profiles per run.
- Generate screen; three options side by side with score and broken constraints.
- A read-only grid of one option, by class and by teacher (moved here from plan 8 so the first
  demo has something to look at).
- Done when: a run on the staging demo board stores three options and each opens as a grid.

### Plan 6: constraints (track B, encoders by track A)
- Migration 0024: `tt_constraints`. Type registry in `lib/timetable/constraints/`.
- Management constraints aimed at a teacher, a class, a grade, a subject or a profile label;
  the form shows how many teachers a label reaches and lists unlinked ones.
- Board status `collecting`, deadline, who answered, fill in for a teacher.
- The demo seed gains a constraints step: all teachers labelled מתמטיקה share a two-period
  consecutive meeting; a management meeting; about one teacher in ten unavailable on one day;
  a free day per entitled teacher, skewed to Friday and Sunday so some must be broken.
- Types and their solver parameters (frozen here):

| Type | Entered by | Solver sees |
|------|-----------|-------------|
| `teacher_free_day` | teacher (if entitled) or management | `{ teacherIds, day }` |
| `teacher_unavailable` | management | `{ teacherIds, day, periods? }` |
| `meeting` | management, aimed at a label or a list of teachers | nothing: the export adds a block with no classes, those teachers, `weeklyPeriods`, `consecutive` |
| `subject_max_per_day` | management | `{ max }` |
| `class_no_gaps` | management | `{}` |
| `teacher_few_gaps` (soft) | management | `{}` |

- `label_common_free_periods` from the spec waits; `meeting` covers the cases named for the demo.
- Done when: constraints appear in the export, and the seeded ones show up in an option's
  broken-constraints list on staging.

### Plan 8: edit, publish, teacher view (track A)
- Drag a lesson with instant double-booking checks; full report via `evaluate`; pin and regenerate.
- Publish; print styles (A4, monochrome-legible).
- `/timetable/me`: own constraints before the deadline, own week after publishing. Built last;
  the demo can run without it because the seed fills the teachers' constraints.
- Done when: the principal flow passes an e2e test, then the teacher flow.

## Deferred, with the reason

- `tt_school_settings` and the default week on `/platform/schools`: every board starts from one
  week in code (`DEFAULT_WEEK`, Sunday to Thursday 8 periods, Friday 5). Add the table when a
  school needs a different week; it takes the next free migration number.
- Running the solver on a real school's data: when a school supplies a file. Until then the
  250-teacher number in the spec is tested on synthetic data only.
