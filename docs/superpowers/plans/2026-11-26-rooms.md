# Rooms (חדרים) + Profile Permissions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let principals set up rooms, their school day and weekly room use, and let staff whose profile grants it see every room's day and book free periods.

**Architecture:** Track A adds permissions to admin-assigned profile options and one resolver, `getPermissions(user)`. Track B adds the `rooms` service: five RLS tables, domain code in `lib/rooms/`, and REST routes under `/api/v1/rooms`, all guarded by `requireRoomsPermission`. Track C adds the `/rooms`, `/rooms/[id]` and `/rooms/manage` pages on top of B's API.

**Tech Stack:** Next.js 15 App Router, Drizzle + `pg`, Postgres RLS, Zod, next-intl, Vitest (real Postgres), Playwright.

**Spec:** `docs/superpowers/specs/2026-11-26-rooms-design.md`

Until then, B can temporarily stub it as `user.role === "admin"`. Each track is merged into `staging` on its own PR. The spec, this plan and the PR template rules in CLAUDE.md apply.

## Global Constraints

- Migrations: A = `db/migrations/0029_profile_permissions.sql`, B = `db/migrations/0030_rooms.sql` (staging ends at 0022, but `feature/timetable` holds 0023–0028 and the staging DB has applied them, so start at 0029 to keep the order when the timetable returns). Never edit an existing migration.
- Every school-data query goes inside `withSchool(schoolId, fn)`. Every new table gets ENABLE + FORCE RLS and the `school_isolation` policy, plus RLS positive + cross-school denial tests.
- Zod on every request body/query and every response. 401 unauthenticated, 403 `Forbidden` / `service_disabled` / `demo_disabled`, 404 unknown id, 400 `Invalid input`, error bodies are `{ error: code }`.
- Permissions: `PERMISSIONS = ["rooms.book", "rooms.manage"]`; `rooms.manage` implies `rooms.book`; `role === "admin"` holds all; only `status === "active"` users hold any.
- Limits: room name ≤ 60 chars, slot label ≤ 60, booking note ≤ 200, ≤ 12 periods a day, days 0–6 (0 = Sunday), times `HH:MM` (`TIME_OF_DAY_RE` from `lib/datetime.ts`), dates `YYYY-MM-DD` in Asia/Jerusalem.
- Strings via next-intl (`messages/he.json` first, `en.json` mirror); CSS logical properties only; icons from `lucide-react`; functions < 50 lines, files < 400 lines; no `any`.
- Demo users (`isDemoUser`): read allowed where their permissions allow it, every write → 403 `demo_disabled`.

## Review Focus

1. A staff member sends `PUT /api/v1/profile` with an option id from an admin-assigned category: expect 400 `admin_assigned`, and the admin-set labels survive a normal self-save untouched (A3).
2. Two bookings for the same room/date/period at the same time: exactly one succeeds, the other gets 409 `slot_taken` (B5, concurrent `Promise.all` test).
3. Booking today a period whose end time has passed (Asia/Jerusalem wall clock, also around midnight UTC): 422 `period_over` (B5).
4. A weekly slot released for one date is bookable on that date only, and the following week it is still occupied (B4/B6).
5. A deactivated staff member who still holds a "מורה" label: 403 on every rooms route (A2/B2).
